00

The one-paragraph version

Only a single demand lineage is wired end-to-end: the ROS / Excel engine, computed weekly and combined by a 2 AM cron. A second demand source — RID-Plan / AquaCrop, delivered as GeoPackage — is ingested and queryable but reaches nothing downstream; the cron is even configured to prefer it, yet the table it reads is never populated, so it silently falls back to ROS.

On the control side, the hydraulic model is a detailed prototype rather than a running loop: automatic demand → opening is stubbed, only 10 of 59 gates are field-calibrated, the physical canal-section limit is a hardcoded constant, and the wired opening formula is numerically inverted — it makes flow fall as a gate opens and returns 287 m³/s for a gate rated 11. Even a correct result couldn't be actuated: the SCADA service accepts only 4 discrete gate levels and has no link to the hydraulic computation.

04

The reproduced bug: flow runs backwards

Critical · verified by numeric repro

The wired required-opening solver expresses Cs = k1·opening^k2 with opening as a 0–1 fraction — putting gate travel in the numerator where the correct rating curve has Hs/Go (travel in the denominator). With K2 < 0 the exponent's effect flips, and the physical Cs clamp (0.3–1.0) present in the sibling module is omitted.

services/flow-monitoring/src/services/hydraulic_service.py · _calculate_required_opening()
Gate M(0,0) · K1=1.0693 K2=−1.229 · width 4.0 m — wired model vs. correct RID form
Gate openingWired CsWired Q (m³/s)Correct Q (m³/s)
10% open18.12287.1—
25% open5.8893.1—
50% open2.5139.73.6
75% open1.5224.17.7
100% open1.0716.911.9

Effect: flow decreases as the gate opens; a gate rated 11 m³/s reports 287 at 10% open. Newton-Raphson can never reach a realistic target (<~17 m³/s at full open) and pegs the opening at a boundary. Sharpest framing: the module with the correct equation (uses Hs/Go + clamp) carries fake calibration data; the module with real K1/K2 carries the wrong equation. Neither is correct at once.

05

The actuator can't take the answer

Computes

flow-monitoring

Continuous gate opening — metres / percent (e.g. 0.73 m, 47%), from a hydraulic solve over the canal network.

Actuates

scada-gate-control

Discrete levels only: 1 Closed · 2 · 3 · 4 Fully open. Modbus write HR 108 + Coil 17. No hydraulics, no flow input.

The API accepts POST /gates/:id/command-level {targetValue} — a level, not a flow. There is no quantizer from continuous opening to a discrete level, and no reference between the two services in either direction. The field gates are 4-position; the model outputs are continuous; nothing connects them. The operator picks a level by hand.

07

Findings register

CriticalF-01

Required-opening formula is inverted and unclamped

Flow decreases as the gate opens; yields 287 m³/s for an 11 m³/s gate. Newton-Raphson cannot converge to realistic targets.

flow-monitoring/src/services/hydraulic_service.py_calculate_required_opening — Cs = k1·opening^k2, no Cs clamp, fixed depth/head
Fix: use Cs = K1·(Hs/Go)^K2 with real levels and the 0.3–1.0 clamp; add a monotonicity property test.
CriticalF-02

Hydraulic control and SCADA actuator are disconnected

Continuous opening (m/%) vs. discrete level 1–4, with no quantizer and no cross-service reference. Computed setpoints cannot reach the gates.

scada-gate-control/src/domain/gate-level.ts4 levels; API command-level {targetValue}; zero hydraulic refs
Fix: define a flow→level mapping (per-gate rating to nearest safe level) and a command bridge; treat level granularity as a control constraint upstream.
CriticalF-11

Wired network topology is ~76% wrong; six conflicting versions

The gate IDs encode a 59-edge connected tree, but the loaded file has 42 edges with only 14 correct — leaving just 2 of 59 nodes reachable from the source (M(0,0)→M(0,1) is missing). Correct files exist but aren’t used.

flow-monitoring/src/munbon_network_final.json14/59 edges vs canonical · updated.json & complete.json are correct
Fix: adopt munbon_network_updated.json (or regenerate from the gate-ID hierarchy); delete the stale variants; then graph-descendant aggregation resolves A1–A3.

The hydraulic modeling ladder

Open-channel models form a ladder of rising fidelity and rising data cost. The build sits low on it; the API advertises the top rung but backs it with a stub. The right next step is the one the current data can actually feed.

The jump from L2 to L5 is large in both effort and data. L4 is the cheap, high-value rung: it captures the two things L2 misses that operations actually feel — variable travel time and peak attenuation down the long reaches (e.g. LMC_03 at 5.26 km) — while reusing the geometry, roughness and gate curves already in the tree.

10

Minimum-viable diffusive-wave upgrade

A Muskingum–Cunge router per canal reach — the diffusive-wave scheme that reuses Manning and reach geometry, needs no global solve, and degrades gracefully to the current travel-time model when sensors are absent.

Governing form

Drop inertia, keep pressure + friction

∂A/∂t + ∂Q/∂x = q_lateral
S_f = S₀ − ∂h/∂x  (local & convective inertia ≈ 0)
K = Δx / c · X = ½(1 − Q ⁄ (B·c·S₀·Δx))

Celerity c ≈ (5/3)·V from Manning, recomputed per timestep → travel time and attenuation both become flow-dependent.

Internal boundaries

Gates couple the reaches

Each gate stays a stage–discharge link between two routed reaches, using the corrected rating curve Cs = K1·(Hs/Go)^K2. Fixing that equation (F-01) is a hard prerequisite — a router on top of an inverted gate law just moves the error downstream.

couples reach ↔ reach regimes free · submerged · closed
Already in the repo (reuse)
  • Trapezoidal reach geometry → A(h), B(h), R(h)
  • Manning n (0.014 concrete / 0.035 earth)
  • Bed slope + computed canal inverts
  • Network topology (tree, 59 gates) & reach lengths
  • Gate rating curves (10/59 field-calibrated)
  • numpy + scipy — enough to host the router
New data needed (modest)
  • Stage sensors at each zone head — upstream BC + validation
  • Complete per-reach geometry for all ~58 reaches (template has 5)
  • Real per-section design_discharge wired as the capacity limit
  • A short mobile-sensor gauging campaign to calibrate n / celerity

11

Remediation blueprint

The corrected demand→gate pipeline — curing B5/B6/B7/B8 on top of a repaired connected graph and a fixed gate equation. A full reference spec (schema, code, tests) accompanies this report.

B5 · conveyance loss

Seepage flux by lining

Q_seep = s·P·L + λ·Q

Seepage velocity s (concrete 3e-7, earth 1.5e-6 m/s) × wetted perimeter × length, + ~5% operational. Route demand up-tree adding loss so the head gate carries more than Σ field demand.

data lining + geometry — presentcalibrate inflow−outflow
B6 + B7 · rotation

Capacity as a hard resource

Σ_active q·(1+λ) ≤ Q_cap ∀ reach,t

Greedy capacity-aware scheduler: start the highest-priority delivery only if it fits every reach on its path; free capacity as deliveries finish. Only concurrent demand is summed; infeasible sums defer to later slots.

cap real design_dischargeupgrade CP-SAT RCPSP
B8 · branch split

Forward physics + inverse

solve_network already resolves the split via continuity — keep it. Replace the crude optimizer with a head→tail coordinated inverse (corrected Cs=K1(Hs/Go)^K2, capacity-clamped), run per rotation block, then verify forward.

forward ✓ works todayinverse rewrite

Corrected sequence

1
Attach demand — ROS section demand → network node via section_node_map (includes the 20 interior delivery nodes)
2
Aggregate up the connected tree — post-order descendants sum + B5 loss uplift → required flow per reach
3
Check capacity — flag any reach over design_discharge; defer overflow to rotation
4
Schedule rotation — capacity + concurrency + travel-time offsets → time-varying reach targets
5
Inverse per block — coordinated head→tail openings; solve_network verifies the branch split
6
Quantize + command — snap to a discrete gate level within capacity → SCADA command-level (the bridge missing today)
7
Close loop — integrate delivered volume; close when met; re-solve the active set

Preconditions (land first): F-11 single connected graph · F-01 corrected gate equation · F-04 real per-section capacity. With those, steps 1–3 are mechanical; 4–7 are the new build.
